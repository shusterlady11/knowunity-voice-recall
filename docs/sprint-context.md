# Sprint context

Voice-based active recall for Knowunity, a study app.
Web prototype styled as iOS: 390px, dark mode only.

**Concept:** Students speak a concept out loud and Knowie replies in text (a spoken reply may come later, alongside the text).

**Where it lives:** A study-plan step (early, and at the end for full review), plus "Explain out loud" in main chat.

## Decisions
- Voice/keyboard toggle on every screen where the student can answer, because switching input shouldn't break the flow. A correct result has none, since there's nothing left to answer (2026-09-29). The chosen mode carries over to the next question until the student switches back.
- OS mic denied: keyboard mode, slashed mic, no micButton, mic side opens re-enable flow, because the mic can't work without permission.
- Primer declined: keyboard mode, mic still selectable, because permission can still be asked.
- "No thanks" on the confirm screen returns to the launching screen, because the student is never trapped. In the usability test, which has no launching screen, it goes to the end screen (2026-09-29).
- Cancel (an X beside the mic while recording) throws away the take and returns to idle, mic ready, because a fumbled start shouldn't force a bad submission, and idle is where the student can record again, switch to keyboard, or skip.
- Prototype purpose (2026-09-29): a usability test with students on a real iPhone in Safari, deployed over HTTPS, in English, on the team's test phones or a remote participant's own iPhone, opened from the Home Screen as a full-screen web app (no Safari toolbars, so the full height holds and there's no back swipe). On phones that aren't 390 wide, the whole 390×844 design scales to the phone's width; iPhone screens share nearly the same proportions, so it also fills the height. The first remote participant has an iPhone 17 (402×874 points): the design scales to 103%, 844 becomes about 870, leaving about 4 spare points. Links carry a short meaningless code (e.g. /s/k7) that maps to a script stored in the prototype, so the student can't read the plan in the address, and the Home Screen icon keeps that code. The moderator talks a remote participant through Add to Home Screen, and watches through the participant's screen share on the call. Each participant gets role-play tasks per question ("answer this fully", "leave something out", "say you don't know") that match the script, so verdicts make sense to them. This replaces the earlier "happy path only" scope.
- Recall engine (2026-09-29): mocked for now; a real engine (Safari speech recognition + an AI judge) is estimated at 3–5 days and deferred. The mock is one piece with a fake setting that a real one can replace later without touching the screens. A script in the link gives each question its own chain of takes, and each take lists the key points it covers (e.g. q1: 1,2 > 3), plus special takes for "didn't catch that", "I don't know" and "slow". The verdict, combined coverage, next hint and covered count are all worked out from the key points, as a real engine's answer would be. What a student does on one question can't shift another's chain: leftover takes are dropped when they move on, and takes beyond the plan cover nothing new. The transcript is canned per question and verdict, and participants are told beforehand that the words shown are placeholders. No real microphone is used: recordingGlow only breathes, with no ripples, so nothing claims to hear the student; the primer screens show but no browser prompt appears, and a denial is only reachable through "Not now".
- Real recall engine (2026-10-26): replaces the mock in phases, because a scripted verdict can't show whether the loop works for a real student. Until a phase ships, the Recall engine entry above still describes the app.
  1. AI judge first. A server route sends the answer, the question and its key points to Claude, which returns which key points the answer covers, the same shape the mock returns. Verdict, hint, covered count and XP are still worked out from that, and hints stay pre-written so the judge can't give an answer away. Typed answers feed it first, so it can be tested before any mic work. A set of sample answers per question (full, partial, wrong, off-topic, rambling) with the verdict each should get checks the judge before a test relies on it.
  2. Speech-to-text next, from the real mic. The whole take uploads when the student taps stop; no streaming or real-time voice API, since push-to-talk doesn't need it. The provider is picked by comparing ElevenLabs Scribe v2 and OpenAI gpt-transcribe on recordings of real answers.
  3. Spoken replies later: Knowie may read its reply aloud, always alongside the on-screen text, never instead of it.
  Phase 1 choices (2026-10-26, designer): a session is live or scripted, chosen on `/reset` ("Start live session" / "Start scripted session"), because the moderator sets the phone up there and a participant shouldn't see the switch; the splash was considered and dropped, since it shows once per phone, participants see it, and no toggle component exists. A participant's link was always scripted; since 2026-10-28 (designer) every session is live by default, so spoken and typed answers are always listened to and judged, and only "Start scripted session" on `/reset` turns that off. In a live session spoken answers follow the script until speech-to-text. The judge's bar is the specific idea named, not just the general area; a key point's central idea is enough. A judge that fails or passes slowTimeout gives the timed-out result, like a slow scripted take. Model: Claude Haiku 5.5 at low effort, because on the 122-answer eval it agreed as often as Opus 5.5 (119 vs 118) at 1.2s instead of 2.2s typical and about 0.015¢ instead of 1¢ an answer; Opus erred strict, Haiku erred generous, which the brief prefers. Haiku has no server-side refusal fallback, so a refusal gives the timed-out result.
  Phase 2 choices (2026-10-26, designer): OpenAI gpt-transcribe, given the question as context and its bold terms and concept name as keywords, never the key points, so a hint can't put the answer in the student's mouth. Live sessions only: the primer's "Turn on" asks the browser for the mic, and each recording opens and closes the mic, so the phone's mic indicator shows only while recording. One request per take: the recording goes to `/api/judge`, which transcribes it and judges the words; silence or only filler is "didn't catch that". A recording submits itself at 3 minutes (motion.duration.recordingMax), a safety net, not end-of-speech detection. A refused mic means keyboard mode with the slashed mic; tapping it opens `/mic-blocked`, which explains how to allow it in Settings, with Try again and Keep typing. Recordings aren't kept. Voice-reactive ripples in recordingGlow come next, as their own step.
  Unchanged: push-to-talk with an explicit stop, no auto-endpointing, recall only, never trap the student, judge generously, design the wait. The scripted mock stays selectable, so the `tour` walkthrough and scripted sessions still work. API keys live only in `.env.local` and are read by server routes; nothing reaches the browser. Once a participant's answers go to a real provider, the briefing says so and asks their consent, instead of calling the words placeholders.
- Content: 5 questions from what the participants just studied, supplied by the designer. Each has 2–4 key points, a pre-written hint per key point, and a canned transcript for each verdict it can get.
